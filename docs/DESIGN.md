## 1. 목표와 범위

나 혼자 쓰는 비공개 피크민 블룸 장소 도감. iPhone과 PC에서 같은 데이터를 보고, 사진을 올리고, ZIP으로 백업·복원한다.
공식 게임 이미지·로고는 쓰지 않으며, 사용자가 올린 사진과 직접 만든 아이콘만 사용한다.

1차 범위에서 **하지 않는 것**: 오프라인 상태에서 변경을 쌓아 두었다가 자동 전송하는 기능, 실시간(즉시) 화면 반영, 이메일 기반 비밀번호 재설정, 자동 일시정지 방지용 주기적 접속.

## 3. 인증·보안 설계

### 3.1 구조: "보이지 않는 주인 계정"
- Supabase Auth에 **관리자가 미리 만든** 이메일+비밀번호 계정 1개만 존재한다. 방문자가 계정을 만드는 경로는 없다.
- 로그인 화면은 비밀번호 칸 하나. 앱은 설정값의 이메일(`VITE_OWNER_EMAIL`) + 정규화한 비밀번호 + Turnstile 토큰으로 `signInWithPassword`를 호출한다.
- 비밀번호 검증과 저장(해시)은 Supabase 서버가 담당한다. 앱 코드·브라우저 저장소에는 비밀번호를 두지 않는다. 브라우저에는 Supabase가 발급한 **출입증(토큰)**만 저장된다.
- 주인 이메일은 **실제로 메일을 받을 수 없는 내부용 주소**를 쓴다(복구 B 방식). 공개 코드에 들어가도 의미 있는 개인정보가 아니다.

### 3.2 비밀번호 규칙과 정규화
- 길이 6~12자. 허용 문자: 영문(A–Z, a–z), 숫자, 키보드 특수문자(공백·한글 제외).
- **정규화 규칙(모든 경로 공통)**: 규칙 검사 통과 후 영문을 소문자로 바꾼다. 최초 설정, 변경, 로그인, 관리자 복구 SQL 모두 이 규칙을 따른다.
  - 예: `Nomad#2026` → `nomad#2026`
- 규칙 검사는 화면에서 하고, 서버에는 최소 길이 6을 설정한다(최대 12자는 화면 규칙. Supabase의 상한은 이보다 길어 충돌 없음).

### 3.3 Supabase 실제 동작과의 충돌 검토 (결론: 아래 설정으로 충돌 없음)

| 항목 | 잠재적 충돌 | 해결 |
|---|---|---|
| 대소문자 무시 | Supabase는 대소문자를 구분해 비교한다 | 앱이 항상 소문자로 바꿔 보내므로 사용자 입장에서는 구분하지 않게 된다. 관리자 복구 SQL에도 **소문자로만** 넣도록 안내 |
| 비밀번호 필수 문자 조건 | "대문자 필수" 같은 서버 조건을 켜면 소문자 정규화와 충돌 | Password Requirements를 **"필수 문자 없음"**으로 둔다 |
| 안전한 비밀번호 변경(Secure password change) | 켜면 변경 시 **이메일 재인증**이 필요 → 이메일을 받을 수 없는 B 방식과 충돌 | 이 설정은 **끈다**. 대신 앱이 변경 전에 현재 비밀번호(+Turnstile)로 다시 로그인해 본인 확인 |
| 이메일 확인 | 가입 확인 메일을 받을 수 없음 | 관리자가 계정을 만들 때 **Auto Confirm**으로 생성 |
| 이메일 재설정 경로 | Supabase에는 재설정 요청 주소가 기본으로 열려 있음 | 앱에서 기능을 제공하지 않음. 요청이 와도 기본 메일 서버는 팀원 주소가 아니면 발송하지 않고, Turnstile도 요구됨 |
| Turnstile 토큰 | 토큰은 1회용 | 로그인 실패·재시도 시 위젯을 초기화해 새 토큰 발급 |
| 가입 차단 | 가입을 끄면 관리자 생성도 막히는가 | 대시보드의 사용자 추가는 가입 차단과 별개로 동작(인프라 단계에서 실제 확인) |

### 3.4 흐름
- **최초 설정**: 관리자가 대시보드에서 계정 생성(임시 비밀번호, 소문자) → 앱 첫 로그인 → "새 비밀번호 설정" 화면 강제 → 완료 후 도감 진입.
  - "첫 로그인 여부"는 서버의 사용자 정보(app 메타데이터가 아닌, 앱 전용 표 `owner_settings.password_initialized`)로 판단한다.
- **비밀번호 변경**: 설정 → 현재 비밀번호 입력 → 새 비밀번호 2회 입력 → 현재 비밀번호로 재로그인 확인 → `updateUser`.
- **세션**: 출입증 자동 갱신. iPhone Safari는 오래 방문하지 않으면 저장소를 비울 수 있어 재로그인이 필요할 수 있다.
- **로그아웃**: "이 기기에서" / "모든 기기에서" 두 가지.
- **오류 메시지**: 비밀번호 틀림, 로봇 확인 실패, 너무 많은 시도, 네트워크 오류, 세션 만료, 서버 일시정지(프로젝트 정지 상태)를 각각 구분해 표시.

### 3.5 비밀번호 분실 복구 (B 방식)
1. Supabase 대시보드 로그인 → 프로젝트 → SQL Editor.
2. 운영 문서에 있는 복구 SQL에 새 비밀번호(**소문자, 6~12자**)를 넣어 실행.
3. 앱에서 새 비밀번호로 로그인 확인.
- 복구 SQL은 Postgres의 bcrypt 함수로 Supabase Auth의 비밀번호 해시를 직접 바꾸는 방식이다. 공식 문서 절차가 아니라 널리 쓰이는 방법이므로 **3단계에서 실제로 실행해 검증한 뒤** 운영 문서에 확정한다. 검증 실패 시 대안을 먼저 보고한다.
- 대시보드 계정 자체를 지키는 것이 곧 도감을 지키는 것이므로, GitHub·Supabase 계정에는 2단계 인증을 켠다.

### 3.6 서버 측 보호 (UI와 별개)
1. **가입 차단**: Allow new users to sign up = 끔. 익명 로그인 = 끔.
2. **RLS**: 모든 표에 RLS를 켜고 `owner_id = auth.uid()`일 때만 읽기·쓰기 허용. 비로그인(anon) 역할에는 표 권한 자체를 주지 않는다.
3. **Storage 정책**: 비공개 버킷. `{주인ID}/` 폴더 안에서만, 로그인한 주인만 읽기·쓰기·삭제.
4. **서버 함수(RPC)**: 영구 삭제·가져오기·복원 같은 묶음 작업은 DB 함수로 만들고 `SECURITY INVOKER`(호출한 사람 권한으로 실행)로 둬 RLS가 그대로 적용되게 한다.
5. **로그인 시도 제한**: Supabase 기본 IP별 제한 + Turnstile. 제한이 실제로 적용되는지는 배포 환경에서 테스트한다.

### 3.7 비밀 정보 관리

| 값 | 공개 여부 | 보관 위치 |
|---|---|---|
| Supabase Project URL | 공개 가능 | GitHub 저장소 Variables → 빌드 시 주입 |
| Supabase Publishable key (`sb_publishable_…`) | 공개 가능 | 위와 동일 |
| 주인 계정 이메일(내부용 주소) | 공개 가능 | 위와 동일 |
| Turnstile Site key | 공개 가능 | 위와 동일 |
| Turnstile Secret key | **비밀** | Supabase 대시보드(CAPTCHA 설정)에만 입력. 저장소·채팅에 넣지 않음 |
| Supabase Secret key (`sb_secret_…`) | **비밀** | 사용하지 않음. 어디에도 복사하지 않음 |
| Supabase DB 비밀번호 | **비밀** | 사용자 비밀번호 관리자에만 보관 |
| 도감 비밀번호 | **비밀** | 사용자 기억 / 비밀번호 관리자 |

- 빌드 전 소스와 빌드 후 결과물에서 비밀 키(`sb_secret_…`, 예전 방식 관리자 키 등)로 보이는 문자열을 검사해 발견되면 **배포를 중단**하는 자동 검사를 둔다.
- 마이그레이션 SQL은 저장소에 보관하고, 사용자가 Supabase SQL Editor에서 직접 실행한다(DB 비밀번호를 GitHub에 저장하지 않기 위해).

## 4. 데이터 구조

모든 표에 `owner_id uuid not null default auth.uid()` + RLS 적용.

### 4.1 `places` — 장소 (버섯·빅플라워·데코 후보 공통)

| 필드 | 형식 | 규칙 |
|---|---|---|
| id | uuid | 기본키 |
| category | text | `mushroom` / `bigflower` / `deco` |
| deco_category_id | uuid, null 가능 | 데코만 사용. null이면 "미분류". 버섯·빅플라워는 반드시 null |
| name | text | 1~100자, 앞뒤 공백 제거 |
| description | text | 0~2000자 |
| lat / lng | double precision | -90~90 / -180~180. 표시는 최대 소수 7자리, 끝의 0 제거 |
| photo_id | uuid, null 가능 | `photos.id` 참조 (참조 중인 사진은 DB가 삭제 거부) |
| is_favorite | boolean | 기본 false |
| seq | bigint | 자동 증가 등록 순번 (정렬 동점 방지) |
| version | integer | 수정할 때마다 1 증가 (동시 수정 충돌 감지) |
| created_at / updated_at | timestamptz | 수정 시각은 DB가 자동 갱신 |
| deleted_at | timestamptz, null 가능 | 값이 있으면 휴지통 |

### 4.2 `deco_categories` — 데코 분류
id, name(1~50자, 휴지통 제외 이름 중복 금지·대소문자 무시), icon_photo_id(null 가능), sort_order, version, created_at, updated_at, deleted_at, owner_id

### 4.3 `photos` — 사진 대장
id, kind(`place`/`icon`), path(표시용), thumb_path(썸네일, 아이콘은 null 가능), width, height, bytes(두 파일 합), sha256(표시용 파일 지문), created_at, owner_id
- 하나의 사진을 여러 장소가 참조할 수 있다. 참조가 하나라도 남아 있으면(휴지통 항목 포함) 삭제하지 않는다.

### 4.4 `restore_snapshots` — 복원 안전 스냅숏
id, created_at, status(`pending`/`committed`/`rolled_back`/`finalized`), payload(jsonb: 복원 직전의 places·deco_categories·photos 전체), owner_id

### 4.5 `owner_settings` — 앱 설정 (1행)
owner_id(기본키), password_initialized, last_backup_at, schema_version

### 4.6 정렬
- 최신순(기본): `created_at desc, seq desc`
- 오래된 순: `created_at asc, seq asc`
- 이름순: 한국어 가나다(브라우저 `localeCompare('ko')`), 같으면 최신순
- 즐겨찾기 우선: `is_favorite desc` 후 최신순
- 선택한 정렬은 화면 상단에 항상 표시, 카테고리별로 이 기기에 기억(편의 기능).

## 5. Storage와 사진 처리

```
버킷: nomad-private (비공개)
{주인ID}/photos/{사진ID}.jpg     표시용, 긴 변 약 1600px
{주인ID}/photos/{사진ID}_t.jpg   썸네일, 긴 변 약 480px
{주인ID}/icons/{사진ID}.png      데코 아이콘, 약 256px
```
- 업로드 전 브라우저에서 압축(원본은 저장하지 않음). 사진 방향(EXIF 회전) 보정 포함.
- 화면 표시는 **만료되는 Signed URL**. 한 번 받은 주소는 만료 전까지 재사용해 전송량을 아낀다.
- 갤러리는 썸네일, 상세·편집 화면은 표시용 사진.
- **순서 원칙: "새 파일 업로드 → DB 연결 변경 → 안 쓰는 옛 파일 정리"**, 삭제는 **"DB 먼저, 파일은 나중"**. 파일 삭제가 실패해 남는 고아 파일은 설정의 **저장공간 정리**에서 확인 후 삭제한다.
- 사진 없음·로딩 실패 시 카드 모양을 유지하는 대체 이미지 표시.

## 6. 저장·동기화·충돌·오류

- 모든 변경은 즉시 서버에 저장. 상태 표시: 저장 중 / 저장됨 / 실패(재시도 버튼).
- 저장 중에는 버튼 잠금으로 중복 제출 방지.
- **동기화**: 저장 직후, 앱으로 돌아올 때(화면 전환·포커스), 네트워크 복구 시 최신 데이터를 다시 불러온다.
- **충돌**: 수정 시 처음 불러온 `version`과 서버 `version`이 다르면 저장하지 않고 "다른 기기에서 먼저 수정됨" 안내 → 서버 내용 보기 / 내 내용으로 덮어쓰기 / 취소.
- **오프라인**: 상단에 "오프라인 — 저장되지 않음" 표시, 저장 버튼 잠금. 작성 중인 글자는 이 기기에 임시 보관해 잃지 않게 한다. **자동 전송한다고 표시하지 않는다.**
- 업로드·가져오기·백업·복원은 진행률과 구체적인 오류 메시지를 표시한다.

## 7. 삭제와 휴지통

- 삭제 → 확인 → 휴지통 이동(`deleted_at` 기록) → 화면 아래 "되돌리기" 버튼 몇 초 표시.
- 휴지통: 목록, 개별 복구, 영구 삭제(추가 확인). **자동으로 비우지 않는다.**
- 영구 삭제는 서버 함수 하나로 처리: 행 삭제 + 더 이상 참조되지 않는 사진 행 삭제 → 지울 파일 목록 반환 → 앱이 파일 삭제.
- 데코 분류 삭제 시 선택: ① 소속 장소도 함께 휴지통 ② 소속 장소를 "미분류"로 이동. 휴지통에서 장소를 복구할 때 분류가 휴지통에 있으면 분류도 함께 복구할지 묻는다.

## 8. CSV·JSON 가져오기

- 열(CSV): `name, category, lat, lng, description, favorite, deco_category` — 한글 머리글(`이름, 카테고리, 위도, 경도, 설명, 즐겨찾기, 데코분류`)과 `버섯/빅플라워/데코` 표기도 허용.
- 인코딩: UTF-8(BOM 포함 가능)과 CP949(엑셀 한글 저장) 자동 인식.
- JSON: `{ "format": "nomad-atlas-import", "version": 1, "deco_categories": [...], "places": [...] }` (사진 제외. 사진은 ZIP 복원으로만)
- 검사: 필수값, 좌표 범위, 카테고리, 글자 수, 데코 분류 존재 여부(없으면 "새 분류 생성 예정"으로 표시).
- **중복 기준**: 같은 카테고리이면서 위도·경도를 소수점 다섯째 자리까지 반올림한 값이 같으면 중복(기존 데이터·같은 파일 안 모두). 기본 **건너뛰기**, 미리보기에서 행별로 "그래도 추가" 선택 가능.
- 실행: **추가만 하는 단일 트랜잭션**. 기존 데이터는 수정·삭제하지 않는다. 결과: 추가 n / 중복 건너뜀 n / 오류 n.
- 상세 형식 문서와 샘플 파일은 6단계에서 제공.

## 9. ZIP 백업·복원

### 9.1 백업 파일
```
Nomad-atlas-backup-YYYY-MM-DD_HHMM.zip
├ manifest.json  형식 이름, 백업 버전, DB 구조 버전, 생성 시각, 개수 요약, 모든 파일의 크기·SHA-256
├ data.json      places(휴지통 포함), deco_categories(휴지통 포함), photos
└ photos/        표시용·썸네일·아이콘 (압축본만)
```

### 9.2 복원 절차
1. **검증(서버 변경 없음)**: ZIP 구조, 형식·버전, 데이터 형식, 모든 사진의 존재·지문 일치, 장소↔사진 연결. 하나라도 실패하면 중단.
2. **요약**: 백업 날짜, 카테고리별 장소 수, 분류 수, 사진 수, 현재 도감과 비교. 저장공간 여유 확인.
3. **안내·확인**: 현재 도감이 교체된다는 점을 알리고 두 번 확인.
4. **안전 백업**: 현재 도감의 안전 ZIP을 만들어 기기에 내려받게 한 뒤, 서버에 스냅숏(`pending`) 저장.
5. **사진 업로드**: 기존 파일·DB는 건드리지 않음. 같은 지문의 파일이 이미 있으면 건너뜀. 실패 시 재시도/취소(새로 올린 파일만 정리).
6. **DB 교체**: 서버 함수 하나(트랜잭션)로 "현재 데이터 삭제 + 백업 데이터 입력". 실패하면 자동 취소되어 원래 상태 유지.
7. **결과 확인**: 서버에서 장소 수·사진 수를 다시 세어 표시. 옛 사진 파일은 지우지 않고 **"복원 되돌리기"**를 유지.
8. **확정**: 사용자가 "복원 확정"을 누를 때 옛 사진 중 안 쓰는 파일을 정리(`finalized`). 자동으로 확정하지 않는다.

### 9.3 실패 시 상태

| 실패 시점 | 기존 도감 | 복구 |
|---|---|---|
| 1~4 | 변화 없음 | 없음 |
| 5 사진 업로드 | 변화 없음 | 재시도 또는 취소 |
| 6 DB 교체 | 트랜잭션 취소로 변화 없음 | 재시도 |
| 7 이후 결과가 이상함 | 교체됨 | "복원 되돌리기" → 스냅숏 데이터 재입력(옛 사진 그대로 있음) |
| 앱이 중간에 꺼짐 | 단계에 따라 위와 같음 | 다음 접속 시 `pending`/`committed` 스냅숏을 감지해 이어서 진행·되돌리기 선택 화면 표시 |

- 큰 백업(수백 MB 이상)은 iPhone 메모리 한계가 있어 PC 사용을 권장한다.
- 무료 플랜에는 자동 백업이 없으므로 앱 상단에 "마지막 백업: n일 전"을 표시한다.

## 11. 무료 플랜 운영 (2026-10-09 공식 페이지 기준, 변경될 수 있음)

**Supabase Free**: DB 500MB/프로젝트, 파일 저장 1GB, 전송량 5GB + 캐시 전송량 5GB, 파일당 최대 50MB, 활성 프로젝트 2개, 자동 백업 없음, 서버 이미지 변환 없음.
- 무료 프로젝트 2개 제한은 **Organization 안의 Owner·Admin 기준**으로 계산되며, 일시정지된 프로젝트는 개수에 포함되지 않는다 → 새 Organization에 만들면 기존 프로젝트와 겹치지 않는다.
- **자동 일시정지**: 1주일간 활동이 적으면 정지(약 1주 전 경고 메일). 정지 중에는 앱이 작동하지 않으며, 대시보드에서 **Resume project**로 직접 재개한다. 재개 가능 기간은 공식 문서상 정지 후 최대 1년이지만, 안전하게 **오래 방치하지 않는다**. **정지 방지용 주기 접속은 만들지 않는다.**
- 정지 중 데이터는 보존되지만 무료 플랜이 이를 보장하는 백업 수단은 아니므로, ZIP 백업을 기기에 보관한다.

**GitHub Pages(Free)**: 공개 저장소만 가능, 사이트 1GB, 월 100GB 전송량·시간당 10회 빌드(권장 한도).

**Cloudflare Turnstile**: 무료 플랜 사용.

결제 수단을 등록하지 않으므로 자동 과금은 없다. 한도를 넘으면 서비스가 제한될 수 있다. 비용이 생길 수 있는 작업은 사전에 알린다.
